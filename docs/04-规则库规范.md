# 04 规则库规范

## 1. 规则文件

规则放在 `data/rules/*.json`，按主题分文件：`time.json`、`people.json`、`ticket_type.json`、`format.json`……

单条规则的格式：

```json
{
  "id": "R-HOT-001",
  "title": "一级动火工作票有效期不超过 24 小时",
  "ticket_types": ["一级动火工作票"],
  "check": "duration_max",
  "params": {"start": "plan_start", "end": "plan_end", "hours": 24},
  "severity": "error",
  "message": "一级动火工作票计划时间为 {actual_hours} 小时，超过有效期 24 小时。",
  "basis": {
    "doc": "《中国南方电网有限责任公司电力安全工作规程第3部分：配电》释义",
    "clause": "21.3.5.3",
    "text": "一级动火工作票的有效期为24h，二级动火工作票的有效期为120h。动火作业超过有效期，应重新办理动火工作票。",
    "source": "2026.9典票库 脚注"
  },
  "tests": {"hit": ["syn-hot-001"], "miss": ["D5-S03"]},
  "status": "draft"
}
```

字段说明：

- `check` 必须是 `rules/engine.py` 里注册过的检查算子，例如 `duration_max`、`before`（时间先后）、`required_field`、`roles_disjoint`（角色不得兼任）、`role_required`、`regex`、`ticket_type_in`。**不允许写任意代码表达式**，这样规则文件可以放心交给业务人员维护。
- `basis.text` 必须是 `data/interim` 里能找到的原文（允许节选），由测试自动校验。
- `status` 有三种：`draft`（草稿，只报 info）→ `reviewed`（业务人员确认过）→ `active`（参与正式报告）。

## 2. 规则来源与提取流程

1. **来源清单**：
   - 典票库的 40 条脚注：`data/interim/*.notes.json`；
   - 正文第一章“两票相关文件内容说明”：专人监护和专责监护的条款、审核把关责任、资质核验口径；
   - 每个场景下的“风险预警”“易出现违章”标注。
2. **人工和 AI 协作提取**：AI 可以根据原文起草规则 JSON，但 `status` 只能设为 `draft`。必须由业务人员核对后才能升级。
3. **每条规则都要附测试**：至少一个应命中的样本和一个不应命中的样本，还要跑全部典票零误报的回归测试。

## 3. 第一批候选规则（摘自典票库，待核对）

### 3.1 优先做：对应需求方点名的四类高频问题

| ID | 高频问题 | 规则 | 依据 | 检查算子 |
|---|---|---|---|---|
| R-CREW-001 | 人员数量 | 总人数 = 1 + 工作班人员数 | 票面一致性 | count_eq |
| R-CREW-002 | 人员数量 | 人员变更（增加或退出）后，在场人数与变更记录一致 | 票面一致性 | count_eq（作用于变更栏） |
| R-LOC-001 | 工作地点 | 工作地点应注明站名、线路名称、设备双重名称和起止杆号 | 票面栏目要求 | regex（模型兜底） |
| R-LOC-002 | 工作地点 | 工作地点或任务里出现的线路，应包含在“停电设备或线路名称”和安全措施所涉及的线路之中 | 票面一致性 | 实体集合比较 |
| R-LOC-003 | 工作地点 | 同一条线路上，工作地点的杆号应位于各端接地点之间（杆号能比较大小时） | 释义 6.4.4（检修范围应封闭接地） | 实体加区间比较；杆号无法比较时只报提示 |
| CMP-* | 安全措施漏项或写错 | 对照典票场景的 `required_measures` 逐条比对；大号侧和小号侧、开关编号不一致的报“疑似写错” | 各场景的典票内容和脚注 | 措施比对（规则加模型） |
| R-TYPE-001 | 票种选错 | 根据作业内容（是否需要停电、与带电体的距离、作业对象）判断应该使用的票种，与实际票种不一致就报错 | 安规 5.3.3.x 的选票条款（经典票库转述） | 规则初筛加模型 choice 题 |
