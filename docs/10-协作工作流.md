# 10 协作工作流：Claude 规划，Codex 实现，人工核对

> 2026-11-12 起产品代码是 Rust（`rust/`，见 ADR-0006），Python 实现已归档到 `archive/`。下文流程不变，路径和命令换成 Rust 的：
> 验收测试写在 `rust/tests/tests/*.rs`，任务卡的 `allow` / `protect` 写 `rust/...` 路径（`protect` 要写完整路径，不支持通配符）；
> 门禁检查改动范围、行数预算、禁用写法、依赖白名单，并跑 `cargo fmt --check`、`cargo test`、`cargo clippy -D warnings`。
> Codex 在沙箱里用仓库自带的工具链（`tools\codex\cargo.cmd`，离线），不再需要复制 Python 运行时。
> Rust 移植本身没有走这套流程（需求方要求先跑通），由规划者直接完成并用对拍验收；T-011 起恢复走卡片。

## 1. 为什么这样分工

| 角色 | 强项 | 弱项 | 在本项目中负责 |
|---|---|---|---|
| **Claude（规划者）** | 理解业务、发散思考、定接口、评判设计取舍 | 让它写所有代码，成本高也没必要 | 拆任务、写任务卡、**先写验收测试**、写参考实现验证卡片、评审、维护文档 |
| **Codex，gpt-6.1-sol，high（实现者）** | 按明确规格把代码写对，执行稳定 | 爱过度设计，防御性代码多，发散能力弱 | 按任务卡实现，跑测试，按固定格式汇报 |
| **人（需求方和业务专家）** | 懂电力业务，有权做决定 | 时间有限 | 核对规则和黄金集标签，回答待确认问题，批准提交 |

核心思路：**把需要发散和判断的工作留给规划者，交给 Codex 的是收敛好的、能机械验收的任务**。Codex 过度设计的毛病，主要靠三道机械约束来管住：行数预算、文件白名单、禁用写法门禁。光在提示词里说“不要过度设计”，效果有限。

## 2. 一个任务的生命周期

```
① 规划（Claude）
   拆出任务 → 写任务卡 docs/tasks/T-xxx-*.md
   写验收测试 tests/test_txxx_*.py（写进 protect，Codex 不能改）
   在仓库外写一个参考实现，验证卡片可行，并据此定出行数预算（约为参考实现的 2 倍）
   提交基线
        ↓
② 派发
   bash tools/codex/dispatch.sh T-xxx
   （codex exec，workspace-write 沙箱，带汇报格式约束；派发时会记录基线提交）
        ↓
③ 门禁（脚本，自动运行）
   tools/gate.py：改动范围 ⊆ allow，protect 文件未改，src/tests 行数 ≤ 预算，
               没有禁用写法，依赖在白名单内，格式、静态检查、测试全部通过
   不通过 → 把门禁输出作为返工意见，回到 ②（续接原会话）
        ↓
④ 评审（Claude）
   读 diff，看设计：是否有多余的抽象、参数、分支，命名和结构是否直白
   有问题 → 写 .codex-runs/T-xxx/review.md，执行 dispatch.sh T-xxx review.md 返工
   最多返工 2 轮。还不行，就由 Claude 直接改写，或者重新拆卡
        ↓
⑤ 收尾
   在真实典票上跑集成检查（由 Claude 执行，Codex 不接触真实数据）
   勾选 08-开发计划.md → 人批准后提交（一卡一提交）
```

## 3. 任务卡怎么写

模板见 `docs/tasks/T-001-典票正文按场景切分.md`。头部字段：

| 字段 | 含义 |
|---|---|
| `id` / `title` / `milestone` | |
| `effort` | 交给 Codex 的推理强度，默认 `high`。纯机械性的任务（照模板写 JSON、改名字）可以写 `medium` |
| `budget_src` / `budget_tests` | 新增代码行数的硬上限（不算空行和注释），按参考实现的约 2 倍来定 |
| `allow` | 允许改动的文件（支持通配符） |
| `protect` | 禁止改动的文件，一般是验收测试 |

正文必须包含这几部分：

- **目标**：一两句话。
- **接口（照写）**：函数和数据结构的签名。由规划者定死，避免 Codex 自己发明抽象。
- **规则**：业务判断，由规划者定好，不要留给 Codex 去猜。
- **不做**：明确列出容易被顺手加上的东西，比如命令行入口、容错、配置项。
- **验收**：指向受保护的测试。
- **规模参考**：参考实现有多少行，这是对 Codex 最有效的“别写多了”的信号。

拆卡原则：

- 一张卡改动的源码控制在 50～300 行，涉及的文件不超过 3 个。
- 一张卡只做一件事，并且能独立验收。
- 需要发散设计的问题（比如怎么建模、选哪种算法），由规划者在卡片里定好，不交给 Codex。
- 有多种可行做法时，卡片里指定一种，并写一句理由。

## 4. 关于 gpt-6.1-sol 的提示词要点

依据公开的最佳实践整理：

- **说清目标和验收标准，不要规定每一步怎么做**。OpenAI 自己的指南也说，过度规定细节反而会降低质量。所以卡片要定死接口和业务规则，但不写实现步骤。
- **AGENTS.md 要短而准**。Codex 每次运行都会读它，上限是 32KiB。长的内容放进 docs，在 AGENTS.md 里给链接。
- **确定性的约束交给配置和脚本**：沙箱模式、模型、推理强度由派发命令的参数决定；格式、预算、禁用写法由门禁脚本检查，不靠提示词里“请注意”这类话。
- **用另一个模型来评审**：一个模型引入的问题，另一个模型更容易发现。这里 Codex 写，Claude 审。
- **小步提交**：一卡一提交，出问题可以随时回滚。
- **关于推理强度**：按你的要求默认用 `high`。但 OpenAI 的建议是从 `medium` 起步，只有评测证明更高的强度确实带来提升时才调高，而且更高的强度不一定带来更好的质量。我们会在前 3 张卡上比较 high 和 medium 两种设置下的代码行数、返工次数和门禁结果，再决定默认值。

## 5. 数据安全（Codex 专项）

- 当前的 Codex 配置通过**第三方中转服务**访问模型。Codex 读到的所有文件内容都会经过这个第三方。
- 因此规定：**Codex 不读 `data/raw/` 和 `data/interim/`**（已写进提示词模板）。它需要的样例，由规划者写进任务卡和测试夹具里，只用最小必要的片段。
- 涉及真实典票全文的集成检查，由规划者在本地执行。
- 门禁只能检查“写了什么”，查不到“读了什么”。Windows 下的 workspace-write 沙箱也不能禁止读取文件。所以这条规定目前靠提示词来约束，属于**软约束**。要做成硬约束，可以把 `data/` 移到仓库目录之外，或者换成官方直连的 Codex 服务。

## 6. 度量（每完成 5 张卡复盘一次）

记录在 `.codex-runs/metrics.md`：

- 每张卡：参考实现行数、Codex 实际行数、门禁失败次数、评审返工次数、推理强度。
- 如果一张卡返工 2 次以上，说明卡片写得不清楚：先改卡片模板，不要急着调提示词。
