# 02 系统架构

## 1. 总体流水线

```
输入：工作票（系统不能导出，但能打印），见下面的“输入渠道”
  │
  ▼
[0] adapters    把各种输入统一转成“票面文本”：保留栏目标签，一个栏目或一个单元格一行
  │               PDF 适配器（主路径）/ 粘贴文本 / 网页 HTML / 扫描件 OCR（兜底，以后再做）
  ▼
[1] ingest      解析：按栏目标签定位字段（标签由《工作票实施规范》统一，和输入格式无关），
  │               识别票种，生成 Ticket 结构，原文保留在 raw_text
  │
  ▼
[2] match       场景匹配：在典票场景库里找到最接近的场景
  │               第一步：按票种和关键词过滤候选场景（规则）
  │               第二步：交给决策层做 choice 题，得到场景 ID 和置信度
  ▼
[3] rules       硬规则校验：时间、有效期、人员兼任、必填项、票种选择
  │               规则读自 data/rules/*.json，置信度固定为 1.0
  ▼
[4] compare     措施比对：把匹配到的典票模板里的每条“必备措施”，逐条与票面比对
  │               先用规则做归一化和字面匹配
  │               匹配不上的，再交给决策层做 noul 题（票面是否存在等效措施），得到概率
  ▼
[5] report      汇总 Finding：按严重度排序，附条款依据和典票对照，输出 HTML / JSON
                置信度低于阈值的，一律标为“需人工复核”
```

### 取数接口契约（取数与解析解耦）

取数方式会变（打印成 PDF → 将来可能换成正式接口），但下游解析不该跟着变。
约定一个中间格式**票面文本**作为边界：任何取数方式只要产出票面文本，解析层就能用。

- 契约定义在 `src/ticketguard/ingest/source.py`（`TicketSource.to_ticket_text() -> str`）。
- 票面文本格式：UTF-8 纯文本，一个栏目或单元格一行，保留栏目标签，表格用 `[TABLE]…[/TABLE]` 包裹（与 `blocks_to_text` 输出一致）。
- **外部取数对接：目前只是占位。** 先保留接口，具体接哪种取数方式要等合规确认（见 `07`）。本仓库不实现任何抓包、爬取代码。更换取数方式时，下游不需要改动。

### 输入渠道（2026-11-05 确认：系统不能导出，但能打印）

| 优先级 | 渠道 | 做法 | 风险 |
|---|---|---|---|
| 1 | **打印成 PDF** | 打印时选择“Microsoft Print to PDF”，或者浏览器的“另存为 PDF” | PDF 字体如果缺少文字映射表，提取出来会是乱码（典票库的 PDF 就有这个问题）。**必须先在内网实测** |
| 2 | 网页另存 / 全选复制 | 如果系统是网页版：Ctrl+S 保存网页，或者 Ctrl+A 全选复制后粘贴 | 复制出来的表格顺序可能会乱 |
| 3 | 纸质打印后扫描，再做 OCR | 兜底方案 | 要额外引入 OCR 模型，准确率和体积都是问题，等前两种渠道都确认不可行再考虑 |
| ✗ | 抓包 | **不做**，见 `07-合规与数据安全.md` | |

设计原则：

- **规则优先，模型兜底**：能写成确定规则的绝不交给模型。模型只回答有限选项的问题（选哪个、是不是），**从不生成文字**。报告里的文字全部来自规则模板和条款原文。
- **每一步都可追溯**：每条 Finding 都记录是哪个模块、哪条规则或哪道题、哪个模型版本产生的。
- **后端可替换**：决策层统一使用 `DecisionBackend` 接口，请求和响应的形状对齐 Jev 的 System One 协议。可选后端有：
  1. `RuleBaseline`：字面、同义词、正则，不需要模型，**第一个上线的就是它**；
  2. `LlamaCppBackend`：本机的 llama.cpp 服务，读取各选项的 logits 得到概率；
  3. `DistilledBackend`：蒸馏并量化后的专用小模型（M7 才做）。

## 2. 模块划分

产品代码在 `rust/ticketguard/src/`（2026-11-12 起，见 ADR-0006）。`src/ticketguard/` 下同名的 Python 文件是冻结的参考实现。

| 模块 | 职责 | 状态 |
|---|---|---|
| `ingest/ticket_parser.rs` | 把票面文本解析成 `Ticket`（字段定位、时间解析、人名和代签解析） | ✅ |
| `ingest/scenarios.rs` | 把典票正文按“场景 N：”切分 | ✅ |
| `entities.rs` | 实体抽取、同义词归一化、措施关键词签名 | ✅ |
| `templates.rs` | 从典票场景生成模板 JSON；运行时读取 `data/templates/` | ✅ |
| `rules/engine.rs` | 加载、校验并执行规则 JSON；8 个检查算子 | ✅ |
| `review.rs` | 场景匹配、措施比对（规则基线，见 ADR-0004） | ✅ |
| `report.rs` | HTML / JSON 报告、打回意见草稿 | ✅ |
| `synth.rs` | 变异算子：从典票生成缺陷票，每张都带“应该检出什么”的标签 | ✅ |
| `evaluate.rs` | 评测：检出率、Wilson 区间、误报清单、场景命中 | ✅ |
| `text.rs`、`time.rs`、`regex.rs` | 与参考实现逐字符等价的换行切分、时间计算、规则正则 | ✅ |
| docx / xlsx 读取 | 把典票库原件转成票面文本 | 未移植，仍用参考实现的 `ingest/office.py` |
| PDF 输入适配器 | 把打印出的 PDF 转成票面文本 | 等内网实测（ADR-0003） |
| 决策层（模型） | 场景匹配重排、措施等效判断 | 第一版不含；方案另行设计 |

## 3. 部署形态

第一版（不含模型）：

```
票审/
  tg.exe                         单个可执行文件，约 2.5 MB；只用 Windows 自带的系统库，不用安装任何运行库
  data/rules/  data/templates/   允许在现场直接更新的 JSON
```

- 把票面文本拖到 `tg.exe` 上：报告生成在票的旁边，并用默认浏览器打开。
- `tg.exe` 从自己所在的目录往上找 `data/`，所以整个文件夹可以放在任何位置。
- 不联网，不监听端口，不写注册表，不启动后台进程（只在出完报告后调用系统自带的 `rundll32` 打开浏览器）。
- 以后如果启用模型，再评估怎么带：llama.cpp 官方版在 Win7 上启动失败（上游 issue #15876），只有非官方分支能跑。

## 4. 关键技术决策（详细见 docs/decisions/）

- ADR-0001：核心功能零第三方依赖（理由：内网环境不一定能 pip 安装，也不好过安全审查）。已部分被 ADR-0006 取代。
- ADR-0002：决策层接口对齐 System One 协议（理由：后端可替换，也能直接复用社区的工具和评测方法）。
- ADR-0004：措施比对用关键词签名（规则基线）。
- ADR-0006：全栈改用 Rust，工具链钉在 1.77.2（理由：目标机器是 Win7；单个小 exe，不带解释器）。
