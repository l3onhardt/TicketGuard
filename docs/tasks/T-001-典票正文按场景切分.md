## 目标

把 ingest 生成的典票库正文文本（一行一个段落，表格用 `[TABLE]…[/TABLE]` 包起来）切分成一个个场景，供 M1 后续任务逐个场景解析。

## 接口（照写）

```python
# src/ticketguard/ingest/scenarios.py
@dataclass
class ScenarioChunk:
    section: str      # 所属段落标题去掉序号，例如 "配电第一种工作票典型场景"
    number: str       # "1"、"12"、"2-1"
    title: str        # 场景标题，例如 "单辐射开关后段线路停电作业（有调整）"
    start_line: int   # 标题所在行号，从 0 开始
    text: str         # 标题下一行起、到下一个场景或段落标题之前的全部行，用 "\n" 连接

def split_scenarios(text: str) -> list[ScenarioChunk]: ...
```

在 `ingest/__init__.py` 中导出这两个名字。

## 规则（由规划者确定，不要改）

1. **段落标题**：整行匹配 `^[一二三四五六七八九十]+、(.*典型(操作)?场景)$`，第 1 组就是 `section`。行尾带页码数字的是目录行，要忽略。只有遇到第一个段落标题之后，才开始识别场景。
2. **场景标题**：在当前段落内，按“下一个期望编号”去找，不是遇到 `场景N` 就切。
   - 期望编号：段落开始时为 1；之后是“上一个主编号 + 1”，或者“上一个主编号-1”“上一个主编号-k+1”（子编号，比如 `2-1`、`2-2`）。
   - 一行中出现 `场景{期望编号}`，后面紧跟 `：`、`:` 或空白，就算场景标题。标题内容取分隔符之后的文本。**这一行前面可以有杂质**：真实文档里有配图文字粘在标题前面，比如 `…110kV南湖站场景5：在电缆沟内作业`。
   - 正文中提到其他编号（比如“参照场景1”）不算标题。
   - 子编号场景（`2-1`）之前的父场景（`2`）也要保留，即使它的正文为空。
3. 遇到新的段落标题时，上一个场景结束。

## 不做

- 不解析场景内部的表格和字段（这是后续任务）。
- 不读文件，不提供命令行入口，不做编码探测。输入就是一个 str。
- 编号不连续时不要“容错”：缺了的编号就是找不到，后面的场景会并进前一个场景里。这种情况由集成测试的计数发现，不要在代码里猜。

## 验收

- `tests/test_t001_scenarios.py`（已写好，受保护）全部通过。
- 其中的集成用例会在真实典票文本存在时运行，要求各段的场景数为：21 / 5 / 4 / 3 / 29 / 30。你不要去读那个文件；这条用例跑不过，就把失败信息写进 `questions`。

## 规模参考

规划者已用一个参考实现验证过本卡：约 35 行代码，全部验收用例都能通过，包括真实文档上的计数。预算 70 行是硬上限。如果你的实现明显超过 50 行，多半是写多了。

真实数据里有一处坑：第二种工作票场景 5 的标题行前面粘着一长串配图文字。“按期望编号查找”这条规则就是为它定的。
