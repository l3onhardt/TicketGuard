# ADR-0007 前端形态：报告页就是前端，做成“审票清单”

- 状态：已采纳（2026-11-12）
- 关联：`01-需求与定位.md` 用户故事 1～3；`08-开发计划.md` 5.3、5.4；T-011

## 背景

需求方要求给项目做一个前端，“一定要让人看得懂、方便看懂”。

用的人是运维单位的工作票接收人、许可人：不是技术人员，在内网办公电脑上用（很可能是 Windows 7，浏览器可能是 IE11）。他拿到一张票，要做的决定只有一个——接收，还是打回；打回就要写理由。

原来的报告（T-010）是照着程序的内部结构排的：候选场景表、疑似问题表、草稿。实际跑下来有四个问题：

1. **“疑似问题 0 条”会被读成“这张票没问题”。** 报告不说机器到底查了什么。场景匹配错、整栏没比对的时候，页面同样是干净的。
2. **露出内部用语**：`D1-S01`、匹配度 0.51、`{线路}{杆号}`、规则编号。审票人看不懂，也不该看到。
3. **最确定的错误显示得最弱**：规则都是草稿状态，人数对不上这种算术事实只显示成一行“提示”。
4. **打回意见草稿是机器腔**，带着场景编号和匹配度，没法直接用。

## 决定

### 1. 形态：一张离线的报告页，用系统浏览器打开

把票拖到 `tg.exe` 上，生成一个自包含的 HTML 文件并用默认浏览器打开。这张页面就是前端。

没有选另外两种形态，理由：

| 形态 | 不选的理由 |
|---|---|
| 原生窗口（内嵌浏览器控件） | Win7 上只能嵌 IE 内核，要写 `unsafe` 的系统调用（红线之外，但门禁禁止，审查成本高）；多出一类“窗口起不来”的故障 |
| 本机网页服务（127.0.0.1） | 要常驻进程、要监听端口。红线 5 只给推理服务留了例外；安全审查时“监听端口”比“一个 HTML 文件”难解释得多 |

代价：报告页不能把数据写回磁盘。需要写回的功能（标记误报、累计反馈）留到以后单独设计，届时再评估形态（T-012 之后）。

### 2. 版式：从上到下回答审票人的四个问题

| 区块 | 回答的问题 | 内容 |
|---|---|---|
| ① 票面身份 | 这是哪张票 | 票号、票种、计划时间、负责人、人数、工作地点和任务 |
| ② 结论条 | 机器查出了什么，我要做什么 | 一句话结论，四种状态（见下） |
| ③ 审票清单 | 机器到底查了哪些，哪些没查 | 每个检查项一行：已查无疑点 / 有需要确认的 / 机器没查 |
| ④ 需要确认的事项 | 具体是什么问题，凭什么 | 每条一张卡片：标题、说明、票面上怎么写的、典票上怎么写的、条款依据 |
| ⑤ 打回意见草稿 | 打回的话怎么写 | 由勾选的事项拼成，可编辑，一键复制 |
| ⑥ 对照的典票场景 | 机器拿哪个场景比的，比对靠不靠谱 | 场景名称、相似度（高/中/低）、另外两个相近场景 |
| ⑦ 局限说明 | 机器的边界在哪 | 免责声明、查不了的事 |

**③ 审票清单是这次改版的核心。** 它让“没报问题”有了明确含义：这一项查过了、没发现疑点；或者这一项机器根本没查。最后固定有一行“机器查不了的项目”，列出必须人工审核的内容。

### 3. 结论条的四种状态

| 状态 | 条件 | 说法 |
|---|---|---|
| `issues` | 有“疑点”（warning / error） | 发现 N 处疑点，请逐条确认 |
| `no_scenario` | 没有找到足够相似的典票场景 | 没有找到对应的典票场景，安全措施没有做比对 |
| `notes` | 只有“提示”（info） | 机器没有发现疑点，有 N 条提示请过目 |
| `clear` | 什么都没有 | 机器检查的项目没有发现疑点 |

优先级从上到下。任何状态都不说“合格”“通过”“没有问题”——机器只查了清单里的项目（红线 3）。

### 4. 用语：页面上不出现内部标识

- 规则编号、措施编号、`D1-S01` 这类场景编号、“匹配度 0.51”、`{线路}` 占位符，一律不上页面。报告 JSON 里保留，供排查和评测用。
- 场景写成“典票场景 1「单辐射开关后段线路停电作业」”；匹配度写成“相似度：高 / 中 / 低”。
- 缺措施时，给审票人看**典票上的原文**（模板新增 `source_text` 字段），并说明这是另一张同类票的写法。
- 打回意见用审票人的口气，一条一句，不带场景编号和匹配度。

### 5. 规则还是草稿这件事，如实告诉用户

规则库没经业务核对之前，规则类发现仍然只显示成“提示”（不擅自升级）。但每张卡片上写明“这条规则还没有经过业务人员核对”，结论条也按“提示 N 条”计数，不让它们消失在页面里。业务核对之后把规则的 `status` 改成 `reviewed`，同一条发现自动变成“疑点”。

### 6. 兼容与可达性

- IE11 能正常显示和操作：JS 只用 ES5；CSS 不用自定义属性、grid、`<details>`。
- 完全离线：样式和脚本内联，没有任何外部地址。
- 不靠颜色单独表达状态：每个状态同时有文字和符号。
- 能打印：打印时隐藏按钮。
- 所有来自票面、规则、模板的文字都转义。

## 后果

- 报告 JSON 的结构变了（新增 `verdict`、`checklist`、`scenario`，`findings` 每条多了给人看的字段）。之前逐字节比对报告的基准测试撤掉，改成结构化断言（`rust/tests/tests/t011_report.rs`）。
- 相似度的三档（高 ≥ 0.60，中 ≥ 0.45，低 < 0.45）只影响显示，不影响是否比对（那个阈值仍是 ADR-0004 的 0.3）。三档的分界是按 ADR-0004 的实测分布定的初值，等有了真实票的反馈再校准。
- “场景匹配错”的根本解法（在页面上切换候选场景、看各自的比对结果）不在这一版，排在 T-012。
