# ADR-0010 一条流水线：规则 → 模型 → 结论；准确度由机器自己考出来

- 状态：已采纳（2026-11-13，需求方要求）
- 关联：ADR-0008（模型复核）、ADR-0009（主界面；本文改掉了它第 2 节的“选模式”和第 4 节的启动时机）；T-022

## 背景

T-021 的主界面让用户先选“规则模式 / 模型模式”再预审。需求方的意见有两条：

1. 做成一个各部分互相配合的完整产品：先过规则，再过模型，最后能看到准确度。
2. 工具是替人省事的。不能让人审一遍、机器再审一遍，更不能让审票人给机器逐条打分——“我都用人审了，为什么不直接把工作做完”。

规划者中途提过一版“审票人逐条点属实 / 误报，累计成准确度”，被需求方否掉了，否得对：那是开发者想要的数据，不该由用户出力。本文记下改正后的设计。

## 决定

### 1. 审票人只做一件事：放入票面，点“开始预审”

没有模式可选，没有要打分的地方。两种“模式”变成流水线上的两步，由程序自己走：

```
放入票面 ─→ ① 规则检查 ─→ ② 模型复核 ─→ ③ 结论 + 需要看的事项 + 打回意见草稿
             0.1 秒         只在需要时才做
```

- **① 规则检查**先出结果，页面立刻显示。
- **② 模型复核**只在规则报了“可能缺少措施”（`CMP-MISSING`）时才做。没有这类疑点，就不启动模型——大多数写得规范的票一两秒就出结论，不用等模型，也不占那 2 GB 内存。模型只可能把疑点降成提示（ADR-0008），所以这一步的效果就是**审票人要看的疑点变少**。
- **③** 页面上用一句话说清楚每一步做了什么（“规则发现 2 处疑点 → 模型认为其中 1 处只是写法不同 → 需要你看的疑点 1 处”），下面就是报告和写好的打回意见草稿。

这台电脑用不了模型（没有 `models` 文件夹、系统太旧、内存不够）时，第 ② 步显示“没有做”和原因，流水线照常出结论。

报告页底部的反馈区（T-014）保留，但只是可选项：使用说明里不再要求“每张票都反馈”。

### 2. 准确度：机器做带标准答案的考题，成绩单随程序带着

单张真实票没有标准答案，机器没法给自己打分。能客观量出来的只有一种：**拿一批知道正确答案的考题，让流水线先过规则、再过模型，数对了多少。** 这件事在开发机上做，结果写进 `data/accuracy.json`，主界面的“准确度”页把它显示出来：

- 第一步规则检查：改错的票查出了多少、没错的票误报了多少、场景选对了多少。
- 第二步模型复核：规则的误报救回了多少、真缺的放走了多少。
- 考题是什么、不能说明什么（不是真实票；规则说“有”的不再问模型；机器查不了的事）。

不在用户的电脑上现场重考：结果是确定的（规则无随机，模型温度为 0），重考一遍要几分钟，对审票人没有用处。

**现在的缺口，如实记下**：规则那一节的数字是 `tg eval` 一条命令出的；模型那一节的数字还是仓库外的脚本量的（ADR-0008 第 6 节），手工填进 `data/accuracy.json`。要做到“打包时一条命令重新生成整张成绩单”，得先把模型复核做进 `tg eval`（T-015）。在那之前，改了模型或 harness 设置的人必须手工重测、手工改这个文件。

### 3. 模型的启动时机（改 ADR-0009 第 4 节）

主界面里，第一次遇到“规则报了缺少措施”的票时才启动模型程序，之后留着复用到程序退出。一直没遇到就一直不启动。

## 没有选的方案

| 方案 | 不选的理由 |
|---|---|
| 让用户选模式（T-021 的做法） | 用户没有理由选“差一点的那个”；多一个要理解的概念 |
| 审票人逐条确认，累计成准确度 | 让用户替开发者干活，违背工具的目的（需求方否决） |
| 每张票都过模型 | 没有疑似缺项时模型无事可做，白等十几秒 |
| 在用户电脑上现场跑考题 | 几分钟，结果和随包带的一样 |
| 页面上显示每条的“把握 xx%” | 模型的把握没有校准过（ADR-0008），显示数字会被当成概率 |

## 后果

- 页面服务的 `check` 接口把 `mode` 换成 `stage`（`rule` / `full`），多返回几个计数；新增 `accuracy` 接口。
- `main.rs` 的 `check_text` 拆成“预审”“模型复核”“写报告”三步，主界面在中间决定要不要启动模型。命令行和拖放的行为不变。
- 新增 `data/accuracy.json`，随交付包带着。
- 版本号升到 0.3.0。
